# Forge — Risk Review

**Status:** Draft for review. Each risk states severity (impact if realized) and likelihood (probability of occurring, given no mitigation) independently, per standard risk-review convention — a low-likelihood, high-severity risk is not the same as a high-likelihood, low-severity one, and this document does not collapse the two into a single score.

---

## 1. Hidden coupling

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| **The Rx Engine's dependency on Movement Identity resolution (Programming v1.2 §5) creates a de facto coupling: Rx classification quality is capped by FCKB's alias/confidence work, regardless of how well the Rx Engine itself is built.** | High — a poorly-resolved Movement Library silently degrades every downstream classification, leaderboard, and analytics signal that depends on `classifiedTier`. | High — FCKB's own review already documents real, live collision cases (SDL/DB/SC/AB/SB) that are unresolved today. | Sequence FCKB's required revisions (`FCKB_ARCHITECTURE_REVIEW.md` §16) strictly before generalizing the Rx Engine's movement-dimension comparison, exactly as `SCORING_DOMAIN_ARCHITECTURE_INVESTIGATION.md` §16.3 already names. Track `confidenceScore` (`RX_ENGINE_SPEC.md` §2) as a first-class, queryable field so degraded classification quality is visible in aggregate, not hidden. |
| **WorkoutVersion, though owned by Programming, exists specifically because Results needs it (`PROGRAMMING_DOMAIN_V1_2.md` §1) — this is a real, if narrow, coupling of Programming's own internal data model to a downstream consumer's requirements, in tension with "Programming has zero awareness Results exists."** | Medium — does not violate the reference-direction invariant (I-15), but is a genuine design-pressure coupling worth naming honestly rather than denying. | Certain (this is a stated fact of this package's design, not a probabilistic risk). | Named and accepted, not mitigated away: WorkoutVersion's *justification* references Results' needs in this document's own reasoning (`PROGRAMMING_DOMAIN_V1_2.md` §1), but its *implementation* has zero Results-domain dependency — Programming would benefit from WorkoutVersion's audit-trail and rollback value even if Results did not exist. The coupling is in the design's motivating narrative, not in the shipped dependency graph, and this document is explicit that a reviewer should verify the latter, not the former. |
| **The Variant Generation Engine and the Rx Engine share the same Movement Library and, implicitly, the same notion of "easier substitution" — a change to that substitution table affects both generation quality and classification accuracy simultaneously, in ways that are easy to test independently and easy to miss in combination.** | Medium | Medium | Add an integration test suite that exercises both engines against the same fixture Movement Library changes, not just unit tests per engine — named here as a required test-strategy addition, not designed further in this analysis-only package. |

## 2. Scaling risks

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| **Competition-mode leaderboards (`LEADERBOARD_RULES.md` §9) introduce a burst-write pattern (thousands of near-simultaneous logs during a live Open/Quarterfinal scoring window) that ordinary daily-training write volume does not.** | High during a live competition window specifically; negligible otherwise. | High, once competition mode is used at all — this is a predictable, not a rare, pattern. | Named explicitly in `SCORING_DOMAIN_ARCHITECTURE_INVESTIGATION.md` §15.2 as the concrete trigger condition for Results v1.0 §16's deferred materialized-leaderboard-cache evolution item. This package does not build that cache preemptively; it names competition mode as the point at which building it becomes justified, consistent with the "never pre-built speculatively" discipline both frozen documents already apply elsewhere. |
| **RenderedVariant caching at scale (thousands of gyms, millions of Workout views) could grow unbounded if cache eviction is not actively managed.** | Medium | Medium | Content-addressed caching (`VARIANT_GENERATION_ENGINE.md` §3.2, §6) with LRU-style eviction already named as the correct policy; this is a standard, well-understood cache-management pattern, not a novel risk this architecture introduces. |
| **AnalyticsEvent, as an append-only stream growing indefinitely across millions of Results over a 5-year horizon, requires either partitioning/archival strategy or increasingly expensive full-replay rebuilds (I-10).** | Medium | High, at genuine 5-year, thousands-of-gyms scale. | Named as a required operational-maturity item, not designed to completion here: a full-history replay remains *correct* at any scale (it is a pure function), but "correct" and "fast enough to run routinely" diverge as volume grows. A windowed/incremental aggregation strategy (recompute only the delta since the last known-good aggregation checkpoint, falling back to full replay only for genuine rebuilds) is the standard mitigation pattern and should be scoped as its own implementation-phase concern once real volume data exists — exactly the same "warranted only if real read-latency at scale demands it" discipline this package already applies to Leaderboard caching. |

## 3. Migration risks

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| **Backfilling `canonicalName` and Movement resolution over years of existing free-text `wods` data (`PROGRAMMING_DOMAIN_V1_2.md` §5) is a large, one-time (or periodically re-run) batch workload that is easy to underestimate.** | Medium | High — `FCKB_ARCHITECTURE_REVIEW.md` §14 already flags this explicitly as a real, non-trivial workload. | Sized and planned as its own project phase, per FCKB's own existing recommendation; this package adds no new backfill surface beyond what FCKB already scoped, but does add a *dependency* (the Rx Engine and Variant Generation Engine both need this backfill to be meaningfully complete before their movement-dimension features can be trusted) that raises the cost of underestimating it. |
| **Existing `wods` rows have no WorkoutVersion at all — a migration must decide whether to synthesize a "Version 1" for every historical Workout retroactively, or to treat pre-migration Workouts as permanently versionless.** | Medium — affects historical-reproducibility completeness (`RESULTS_DOMAIN_V1_1.md` §10) for pre-migration data specifically, not for anything logged after this package ships. | Certain to require a decision (not merely a risk that might occur). | Named as an open migration-strategy question this document does not resolve unilaterally: synthesizing a retroactive "Version 1" from each historical Workout's current (only) state is the simpler option and is recommended, since pre-migration Workouts have no version history to lose (nothing was ever edited-with-detectable-revision in a machine-verifiable way before this package); the alternative (leaving old Results without a `workoutVersionRef`) is explicitly discouraged, as it would create a permanent two-tier historical-reproducibility guarantee (I-1 holds for new data, not old), which this document considers an acceptable but disclosed degradation, not a silent one. |
| **`RenderedVariant`'s `renderedVariantHash` field (`RESULTS_DOMAIN_V1_1.md` §2) has no historical value for Results logged before this package ships, since no RenderedVariant computation occurred at their original logging time.** | Low | Certain for pre-migration data. | The field is nullable for pre-migration Results; its absence does not weaken any other guarantee (Scoring Snapshot's core interpretive fields remain valid regardless), and this is disclosed here rather than silently backfilled with a fabricated value, consistent with Results v1.0 §14.1's "never discarded, never guessed away" migration discipline. |

## 4. Performance bottlenecks

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| **The Rx Engine's decision matrix (`RX_ENGINE_SPEC.md` §3) runs per-dimension comparisons synchronously at write time on every Result — a multi-movement, multi-dimension Section could make this meaningfully more expensive than today's single-Load-comparison `rxEngine.js`.** | Medium | Medium | The comparison set is bounded by a Section's own Movement count (typically single digits), not by data volume — this scales with authoring complexity, not with platform growth, and is not a genuine "thousands of gyms, millions of Results" scaling risk in the way AnalyticsEvent volume (§2 above) is. Named for completeness, assessed as low real risk. |
| **View-time rendering (`VARIANT_GENERATION_ENGINE.md` §2) adds a computation step to every Workout view that did not exist before this package.** | Low, given caching (§3.2) | Medium without caching, Low with it | Content-addressed caching is specified as the default expected deployment, not an optional afterthought — a cold cache still produces correct output, only marginally slower, and cache warm-rates are expected to be very high given most athletes at a gym view the same WorkoutVersion/ScalingContext combinations repeatedly through a day. |

## 5. Concurrency issues

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| **Race condition: a coach edits a Workout (creating WorkoutVersion N+1) between the moment an athlete opens the Workout (rendering against WorkoutVersion N) and the moment that athlete logs a Score.** | Low-Medium — the athlete's Scoring Snapshot correctly pins to whichever WorkoutVersion was current *at the moment of logging* (not at the moment of viewing), which could differ from what they saw on screen if this race occurs. | Low — requires a coach edit to land in a narrow window during active athlete logging, an infrequent real-world occurrence. | `renderedVariantHash` (`RESULTS_DOMAIN_V1_1.md` §2) exists specifically to make this race *detectable* after the fact (comparing the hash of what was rendered against the hash the eventual WorkoutVersion-at-log-time would produce) even though it is not prevented — a disclosed, auditable edge case rather than a silent inconsistency. Preventing it outright (e.g., locking a Workout against edits while any athlete has it open) is explicitly rejected as disproportionate — it would violate Programming's own "coach must be able to correct mistakes without friction" principle for an edge case with low real-world frequency and a low-severity, fully-auditable consequence. |
| **Two athletes submitting a tied, leaderboard-adjacent score simultaneously during a competition-mode scoring window (`LEADERBOARD_RULES.md` §9) — does rank order depend on write-arrival order, and is that fair/deterministic?** | Low | Medium, specifically during high-traffic competition windows | Leaderboard rank is computed at read time from final, persisted Result data (I-11) — write-arrival order has no bearing on rank; rank is a pure function of Score value (and Tie-Break Key, if declared) evaluated *after* both writes are durably committed, not a function of commit sequence. No new concurrency-control mechanism is required beyond ordinary write durability, which this package assumes as a platform-level guarantee already provided beneath every domain. |

## 6. Multi-tenant risks

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| **VariantGenerationRuleSet, MovementLibraryEntry substitution tables, and Load/Rep reduction percentages are gym-configurable (`PROGRAMMING_DOMAIN_V1_2.md` §12) — a misconfigured gym-specific Rule Set could silently produce implausible generated content (e.g., a 95% load reduction) with no cross-gym signal to catch it.** | Medium | Medium | Coach review-before-accept (`PROGRAMMING_DOMAIN_V1_2.md` §8, Architecture Principle 4) is the primary mitigation — no generated content reaches an athlete without explicit coach acceptance, regardless of how implausible the underlying Rule Set is. A secondary, not-yet-designed mitigation worth naming: a platform-level sanity-bound check (e.g., "flag, don't block, any generated Load reduction exceeding 80%") as a coach-facing warning, not a hard constraint — named as a recommended V2 addition, not designed to completion here. |
| **Cross-gym leaderboard/Benchmark aggregation (`RESULTS_DOMAIN_ARCHITECTURE.md` v1.0 §16's deferred "World" leaderboard) requires careful gym-scoping discipline everywhere else in this package to avoid becoming an accidental default rather than a deliberate opt-in.** | High if violated (a real tenant-isolation breach), Low if the existing discipline holds | Low, given I-13's existing gym-scoping invariant and its inheritance from a domain that has already been reviewed once for this property | Every new entity in this package (WorkoutVersion, ValidationRecord, AnalyticsEvent, VariantGenerationRuleSet) is scoped by inheritance — WorkoutVersion inherits Workout's gym scope, ValidationRecord/AnalyticsEvent inherit Result's Member-and-gym scope — no new entity introduces an independent, un-scoped identity space. This is a structural property of this package's own design, not merely an aspiration. |

## 7. Future feature risks

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| **Format composition/nesting (competition multi-part events, buy-in/cash-out) remains a named-but-undesigned Programming-domain prerequisite (`PROGRAMMING_DOMAIN_V1_2.md`, `SCORING_DOMAIN_ARCHITECTURE_INVESTIGATION.md` §17 item 2) that this package's own multi-part scoring (`RESULTS_DOMAIN_V1_1.md` §Score Model) and competition-tier analytics (buy-in/cash-out timing, `SCORING_DOMAIN_ARCHITECTURE_INVESTIGATION.md` §11.2) both depend on.** | High for anything competition-tier specifically; zero for ordinary daily-training use of this package | Certain to require resolution before competition-tier features ship, though not before this package's core (daily Rx/variant/leaderboard functionality) ships | Named as the single largest standing dependency this entire package carries forward, unresolved by design (outside this package's authority, per the Absolute Constraint against redesigning frozen domains without explicit new authority). Recommended as the next architecture-investigation mission after this package's own review concludes. |
| **Team/Relay Results (`RESULTS_DOMAIN_V1_1.md` §Score-Model, `SCORING_DOMAIN_ARCHITECTURE_INVESTIGATION.md` §6.4) require Result's Member reference to become many-to-many for this one case — undesigned, and a genuine, non-trivial change to an otherwise-stable core entity if handled carelessly.** | Medium — affects only Team/Relay-scored Results; zero impact on individual-Result-dominant daily use. | Low near-term (no committed timeline named in this package), Medium-to-High if HYROX or Games-style team events become a near-term product priority | Named explicitly as requiring its own dedicated design exercise before implementation, not to be improvised inline when the first team-scored workout is authored — the risk here is specifically *rushing* this design under feature-delivery pressure, not the underlying complexity itself, which is well-understood in the abstract. |
| **Offline mobile logging's interaction with Rx Engine re-validation on reconnect (a device queues a log against a locally-cached WorkoutVersion that has since been superseded server-side) is architecturally sound (`VARIANT_GENERATION_ENGINE.md` §8.5's original reasoning) but operationally untested at this design stage.** | Medium | Medium | The architecture itself handles this correctly by construction (a Scoring Snapshot captured offline still pins to whatever WorkoutVersion was cached on-device at logging time, resolving deterministically on sync per I-1/I-2) — the named risk is exclusively in *implementation verification*, not design: this should be an explicit test scenario (offline log against version N, server has since moved to version N+1, verify sync produces a correctly-versioned Result) in any future implementation phase, not assumed correct from architecture alone. |

## 8. AI integration risks

| Risk | Severity | Likelihood | Mitigation |
|---|---|---|---|
| **The Variant Generation Engine, while deterministic and rule-table-driven in this package's design (not ML-based), could be pressured by future product requirements toward an ML/LLM-based generation approach for richer movement substitution — which would break the determinism invariant (I-6) this package relies on.** | High if it occurs without a corresponding architecture revision; zero under this package's current design | Low near-term, Medium over the full 5-year horizon this package targets, given the platform's own existing AI-assisted-authoring precedent (Programming v1.1 §2) and broader industry direction | Named explicitly as a boundary this package's determinism guarantees depend on holding: **any future move to non-deterministic (ML/LLM-based) variant generation requires its own architecture review specifically addressing how I-4/I-6 determinism (or an explicitly-relaxed, disclosed replacement guarantee) would be preserved** — this package does not pre-approve that evolution, and a reviewer should treat "generation stays deterministic" as a constraint on future work, not merely a description of this package's initial implementation choice. |
| **AI-assisted Programming authoring (already-frozen v1.1 capability) interacting with the new Variant Generation Engine — could an AI-drafted Workout's AI-suggested Metadata or Movement tagging silently lower the confidence/quality of what the Variant Generation Engine then generates from it, compounding two AI-adjacent uncertainty sources into one opaque result?** | Medium | Medium | Both existing AI-authoring (v1.1) and this package's Generation Engine already share the same governing principle — output lands in the ordinary editable surface, is coach-reviewed, never self-publishes, and provenance is never persisted as a permanent visible property (`PROGRAMMING_DOMAIN_V1_2.md` §7, §8). This compounding risk is real but is fully mitigated by the same single mechanism (mandatory coach review before Publish) regardless of how many AI-adjacent steps preceded it — the review gate does not care how the draft was produced. |

**Reading this table**: no risk in this review is rated both High severity and High likelihood simultaneously with no mitigation — every High-severity item either has a concrete mitigation already built into this package's design (competition-mode leaderboard scaling, the AI-determinism boundary constraint) or is explicitly named as requiring future, separately-scoped work rather than being silently assumed solved (format composition, Team/Relay Results, the historical-backfill decision). This is the intended posture for a package submitted for principal-architect review: real risks disclosed at real severity, not minimized to appear more finished than the design actually is.
