## 2026-07-27 — Gym Transfer (M7) closed: identity-based continuity across gyms, Transfer Code fallback
New capability on top of the frozen Member Domain (M1.1-M1.5.5, below): an admin can end a Membership as a Transfer (`memberships.status = 'transferred'`, a value the schema reserved since M1.1 but never populated until now) rather than a Removal. In the ordinary case, the member later joins any gym entirely through the existing, completely unmodified self-service join — Forge recognizes the continuity purely by checking whether their most recent previous Membership ended as a transfer, a read-only derivation over Membership history, never a stored fact. For the case where the member cannot complete that join themselves, a new Transfer Code entity (distinct from the pre-existing gym join-code mechanism, scoped to one specific transfer rather than reusable across joiners) lets the origin admin issue a short-lived, single-use, 72-hour credential the destination admin can redeem on the member's behalf. Tenant isolation is structural throughout both journeys: no gym ever learns which gym a former member joined, or which gym issued a code presented to them.

Preceded by a full, staged architecture cycle before any implementation began, each phase separately reviewed and approved: a Product Specification (M7.1) resolving every business-rule ambiguity; a Technical Architecture (M7.2) reusing the existing gym-change synchronization trigger and self-service join wherever possible and introducing only the Transfer Code entity and its lifecycle as new; an Implementation Plan and Execution Plan (M7.3) breaking the work into 11 independently-reviewed, independently-committed steps; a Freeze Notice formally closing the architecture phase and requiring an ADR for any future change. All four are now persisted as canonical documents, not left as conversation-only artifacts: `docs/architecture/M7_1_GYM_TRANSFER_PRODUCT_SPECIFICATION.md`, `M7_2_GYM_TRANSFER_TECHNICAL_ARCHITECTURE.md`, `M7_3_GYM_TRANSFER_IMPLEMENTATION_PLAN.md`, `M7_3_GYM_TRANSFER_EXECUTION_PLAN.md`, `M7_FREEZE_NOTICE.md`.

Implemented across 11 steps: (1) extended the existing gym-change synchronization trigger's ending branch to write `transferred` instead of `removed` when signaled via a transaction-local setting, defaulting to `removed` when absent — the same trigger Remove Member and self-service join already depend on, touched twice total across this feature (here and again at step 7), with the ending branch's default behavior and the join branch's own logic byte-for-byte unchanged each time; (2) a sibling Edge Function to Remove Member (`admin-transfer-member`), reusing its authorization function verbatim via a cross-function import rather than a copy, differing only in a new, narrow, service-role-only RPC (`end_membership_as_transfer`) that sets the reason signal and clears `profiles.gym_id` in one transaction — required because two separate client calls would be two separate Postgres transactions, losing the signal before the trigger ever saw it; (3) the origin-admin Transfer action in the admin Members screen, its own confirmation state, Remove Member's own code untouched; (4) a read-only Recognition derivation (`member_transfer_recognition()`), security-invoker, relying entirely on the pre-existing `memberships` RLS policy — no new access capability; (5) the `transfer_codes` schema, RLS-scoped to the issuing gym's own admins only, with no INSERT/UPDATE policy at all so no client-side write path exists until the RPCs land; (6) issuance/revocation RPCs, plus a partial unique index (`transfer_codes(membership_id) WHERE status='active'`) as the concurrency-safe mechanism guaranteeing exactly one active code per transfer under genuinely simultaneous requests — application logic alone (supersede-then-insert) cannot guarantee this across independent transactions; (7) a second, narrowly-reviewed extension to the same synchronization trigger, superseding any outstanding active code the instant its transfer completes through the ordinary join, closing a lifecycle gap identified during the technical freeze review; (8) Derived Expiry — a 72-hour window checked at read time via a small stateless helper, never written as a stored status, consistent with the Member Domain's own principle that status should be derived rather than trusted as a stored fact; (9) the origin-admin's post-transfer code panel, working around a genuine, disclosed RLS constraint (an admin cannot look up a former member's identity by name once their gym affiliation has ended) by surfacing issue/view/revoke inline at the moment of transfer, the only point both facts are simultaneously available; (10) the Fallback redemption Edge Function and its own combined RPC (`redeem_transfer_code`), atomically marking a code used and writing the tenancy signal in one transaction, every failure mode (nonexistent/expired/revoked/superseded/already-used code) rejected with the identical generic message, and relying on the pre-existing `prevent_profiles_gym_id_change` guard — untouched — to structurally prevent a redemption from ever overwriting a member's already-set gym; (11) the destination-admin redemption entry point, a new card in the admin Settings tab, displaying the backend's own error message verbatim rather than reinterpreting it.

Every step was validated directly against the linked production database inside rolled-back transactions before being committed — never against a separate staging environment, since none exists (see Architecture Snapshot) — including the full cross-step lifecycle end-to-end (transfer → issue → replace → supersede-on-ordinary-join → recognize; and separately, transfer → issue → redeem-at-a-different-gym → recognize), concurrency proofs for both the exclusivity index and the redemption row-lock, and tenant-isolation checks confirming a cross-gym admin can neither see nor act on another gym's codes. Two implementation-level technical necessities (steps 2 and 10's combined RPCs, and step 6's concurrency index) were identified, flagged explicitly, and confirmed to fall within the frozen Technical Architecture's own stated latitude for implementation choices — not architectural deviations, and no ADR was required at any point across all 11 steps.

11 migrations (`20260727110000` through `20260727180000`), 2 new Edge Functions (`admin-transfer-member`, `redeem-transfer-code`, alongside the pre-existing `admin-remove-member`), 11 commits (`2e3640e` through `8530b6f`). Full reasoning and the complete per-step record: `docs/architecture/M7_FREEZE_NOTICE.md` and the four documents it names above; see also `/docs/DECISIONS.md`.

## 2026-07-27 — Member Domain Migration closed: profiles→members identity bridge introduced, then fully retired (M1.1-M1.5.5)
A new Member Domain (`members`/`memberships`, canonical architecture: `docs/architecture/MEMBER_DOMAIN_ARCHITECTURE.md`) was introduced alongside `profiles` and migrated to in phases, not a hard cutover. M1.1-M1.3 introduced the tables and backfilled them once. M1.4 moved every cross-member read (Feed authorship/roster, Admin rosters, Leaderboard, "who else is booked") to `members`, while `profiles` remained the write target and Source of Truth for identity, kept in sync by a `SECURITY DEFINER` trigger bridge. M1.5.1-M1.5.3 added the RLS `members` needed to accept writes, migrated the Member Portal's own profile read to a merged shape, then retargeted every Member Portal identity write (name, avatar, gender, birth date, weight unit, language, email) directly to `members` — `gym_id`/waiver fields stayed on `profiles`, Membership-owned, unchanged. A dedicated review (M1.5.4) then proved two live regressions the incremental approach had introduced: the still-necessary gym-join/leave trigger was silently reverting identity edits back to a stale `profiles` snapshot on every gym transition, and the manual reconciliation RPC was the same bug's admin-invoked twin — both traced to one shared sync function never revisited after write ownership moved. A separate, empirically proven finding (a real unauthenticated request against the live production API, not an inference): that same function carried unrevoked `EXECUTE` for `anon`/`authenticated` with no internal authorization check. Closed by narrowing the function to create-if-missing only and revoking the exploitable grant (commit `532a4d8`). M1.5.5 then retired the now fully dead trigger/function pair the write migration had made obsolete, confirmed by repository-wide audit to have zero remaining callers (commit `68598b5`). `members` is now the sole Source of Truth for Member identity; `profiles` can no longer propagate identity into it in any way. `profiles.gym_id` and waiver acceptance remain unchanged, Membership-owned, and are a separate, larger, not-yet-started future migration. Full reasoning: `/docs/DECISIONS.md`.

## 2026-07-24 — M13.X closed: Broadcast synchronization for visibility-removing events (Remove Member)
Admin Web reported that removing a member wasn't reflected live in the Admin PWA (Member App). Root-caused to an unavoidable Supabase Realtime platform behavior, not a Forge bug: `postgres_changes` evaluates a subscriber's RLS policy against the row *after* the change, so a `profiles.gym_id → NULL` transition — the row leaving the admin's own visible set — can never be delivered via that mechanism, confirmed independently three times with a raw client bypassing all application code. A full architecture review followed (options: targeted Broadcast, replacing Postgres Changes entirely, a generic Platform Events system), initially recommending Platform Events; explicitly self-challenged against YAGNI/KISS given exactly one real use case exists today, and reversed in favor of the narrower option. **Approved architecture**: Postgres Changes remains primary; a minimal, gym-scoped, private Broadcast channel (`gym:<id>:visibility`) is used only as an invalidation signal for visibility-removing events — never authoritative, clients always re-fetch through existing RLS-protected queries. Implemented as one generic, reusable trigger function (mirrors `prevent_gym_id_change()`'s shared-function convention), one Realtime Authorization policy, and a small `broadcastTopic` addition to `forge-admin-web`'s existing `useRealtimeSync` hook (reusing its channel, not a new one) plus one small dedicated channel in this app's `App.jsx`. A final pre-merge engineering review found and fixed two issues: a `realtime.send()` failure could have rolled back the actual Remove Member mutation (isolated in its own exception block, deployed as a follow-up migration) and a duplicated topic-string literal across two Admin Web call sites (extracted to one shared helper). All four sync directions plus regression on ordinary `profiles` changes validated live in production, zero RLS/tenant-isolation/Financial-Domain regression. Full reasoning: `/docs/DECISIONS.md`.

## 2026-07-21 — M6 closed: real live Stripe payment validated end-to-end; production Stripe account confirmed
Completed what the previous entry left outstanding. A real member click → Stripe Checkout → real card payment → webhook → Subscription activation was exercised against an isolated sandbox gym (CrossFit Tester), on the company's actual production Stripe account (confirmed intentional — this is not a test-mode integration; see `/docs/DECISIONS.md`). Two real issues surfaced and were resolved before the payment succeeded: the Stripe account had not yet completed capability activation (a Stripe-side onboarding gate, unrelated to Forge's code — resolved on Stripe's side, not ours), and one abandoned test Order had a stale Stripe Idempotency-Key that kept replaying a cached failure from before that activation — deleted, letting the next attempt generate a fresh key. Idempotency was then proven, not assumed: the real completed webhook event was replayed against the live `stripe-webhook` function with a genuinely valid signature, and the duplicate was rejected at the Order-status gate before touching Payment or Subscription — zero duplicate rows, confirmed by direct before/after comparison. All 13 of M6's original success criteria and all 13 of P0-006's regression checks now verified with real data; both closed. Full report: `docs/2026-07-21_Financial_Domain_Production_Readiness_Report.md`.

## 2026-07-21 — M6 validation (part 1): two production defects found and fixed (P0-005, P0-006); Stripe end-to-end flow still pending
Preparing for M6's original goal (validating the full Checkout→webhook→activation flow) surfaced two unrelated, real production bugs before that flow was ever exercised. **P0-005**: a deleted client's still-valid browser JWT (Supabase doesn't invalidate already-issued tokens on account deletion) fell through to the ordinary subscription paywall instead of being signed out — fixed by having `fetchUserProfile()` force a sign-out when a profile genuinely no longer exists. **P0-006**: the old `admin-delete-client` deleted `profiles` and `auth.users` outright, silently colliding with `orders`'s protective FK for any client with financial history (real since Phase 2) — replaced end-to-end with **Remove Member**, which only clears `profiles.gym_id` and ends any active subscription (via `end_subscription`, now `service_role`-capable), leaving identity, `orders`/`payments`, and training/social history untouched. Required a narrowly-scoped fix to a shared multi-tenant trigger (`prevent_gym_id_change`) that unconditionally blocked any `gym_id` change — `profiles` alone now has its own variant permitting `<a gym> → NULL`; the shared trigger is otherwise unchanged, still protecting 24 other tables. Both fixes validated with real data end-to-end, including a live authenticated login confirming the new dedicated "No Gym" screen. A separate, unrelated legacy defect (one `auth.users` row orphaned by the old delete operation weeks before Stripe work began) was found and repaired as a one-time data fix. 6 commits (`ab3d55f`...`4fb57cd`), pushed and deployed. Stripe's actual Checkout→webhook→activation flow has not yet been exercised with a real payment — that remains outstanding for the next validation pass.

## 2026-07-20 — Online Payments (Stripe), Phase 5a: RPC authorization layer shipped
Groundwork for member-initiated Stripe Checkout, built on top of the frozen Financial Domain — no Stripe SDK, Checkout Session, or webhook Edge Function exists yet; this phase is purely the RPC-layer trust and authorization model those future pieces will call into. `create_order_for_subscription`, `register_payment`, `create_subscription`, `activate_queued_subscription` each gained a `service_role`-authorized path (tenant resolved from the target row, since `auth.uid()`/`my_gym_id()` are null under that role); `register_payment` gained idempotent retry on `(provider, provider_reference)`; `create_subscription` gained a self-service path that never accepts a caller-attested payment amount and always creates a pending Order immediately; `activate_queued_subscription` gained a paid-Order activation guard blocking any non-admin caller (member or `service_role`) from activating before the Order is `status='paid'`, with admin retaining an unconditional override and the no-Order admin-scheduled-renewal path left untouched. A pre-existing, unrelated defect was found by this phase's mandated validation (not introduced by it): `subscriptions_restrict_member_update()`, part of the waitlist auto-booking system, rejected every `service_role` write to `subscriptions` — fixed with one added bypass clause, every other caller class re-verified unaffected. Two validations were mandatory before sign-off, both passed: idempotency (same webhook/`provider_reference` delivered twice → exactly one Payment, one Order transition to `paid`, one active Subscription) and concurrency (two genuinely lock-forced-parallel sessions on the same order/subscription → same one-each outcome, confirmed via `clock_timestamp()` proving real blocking, not sequential luck). 5 migrations (`20260720130100`–`20260720130500`), all applied and verified live. Full reasoning: `/docs/DECISIONS.md`.

## 2026-07-20 — Financial Domain shipped, closed, and frozen
Regex-parsed `subscriptions.notes` revenue tracking replaced end-to-end with a structured `orders`/`payments` model (`Subscription → Order → Payment (method/provider/provider_reference) → Refund → Reporting`). Five phases: schema (`orders`, `payments`, constraints, triggers, RLS) → core RPCs (`create_order_for_subscription`, `register_payment`, `refund_payment`) → subscription-lifecycle RPCs (`create_subscription`, `activate_queued_subscription`, `delete_queued_subscription`, `end_subscription` — added after a gap analysis found no original RPC actually wrote to `subscriptions`) → application cutover (`saveAbonament`, `adminActiveazaAboQueued`, `activateQueuedSubscription`, `stergeAbonament` rewired to call the RPCs exclusively, legacy `notes` write removed) → reporting migration (`fetchRapoarte`'s revenue figure now anchored on successful `payments` events, not subscription/order creation dates). One post-closure extension: Payment Methods — `payments.method` canonicalized to a closed vocabulary (`cash`/`card`/`bank_transfer`/`comp`, no `'other'`), completing a capability the original schema already had but no code path used; `create_order_for_subscription` widened to admin-or-owner so member self-service activation produces an Order (`register_payment` deliberately left admin-only — see `/docs/DECISIONS.md`). 27 migrations, all committed and verified live. Full ADR record and reasoning: `docs/2026-07-20_Financial_Domain_Architecture_Working_Session.md` (ADR-001 through ADR-013). Every phase validated against real production data (rolled back or explicitly cleaned up), including a genuine end-to-end browser walkthrough for the final phase. Two real bugs caught and fixed before sign-off: `CREATE OR REPLACE FUNCTION` silently creating a duplicate overload instead of replacing when a parameter signature changed arity, and a dropped grants block briefly leaving three RPCs callable by `anon` — both found by checking live state rather than trusting migration output.
