# M10.5 — Platform Purchase Flow: Product Decisions

This document resolves every item `M10.5_PURCHASE_FLOW_READINESS.md` left open, and only those items. No architecture, no Financial Domain rule, and no Stripe integration boundary is touched — every decision below chooses between options that already fit inside what is frozen. Several decisions turned out to already have a live, proven answer once actually checked against the running Member-billing code (`App.jsx`'s existing checkout-waiting screen, its existing "active plan replaces the buy button" pattern) — reused directly here, per Principle 3.7, rather than re-decided from scratch.

---

# Decision 1 — Pending-Payment Experience

**Options considered.**
- **A. Client-side polling** on the Order's own derived status, from the moment the customer returns from Stripe, until it resolves or times out.
- **B. Manual "check status" action** — the customer must click something to re-check.
- **C. Silent redirect, no special screen** — land back on Billing and let its normal, already-fresh read show whatever is true.
- **D. Real-time push** on the underlying tables.

**Decision: A — client-side polling**, read-only, on `platform_orders.status`, at a 3-second interval, with a 60-second timeout into a distinct third state. This is not a new design: it is the exact, live, already-proven mechanism `App.jsx` already runs for Member billing (`checkoutStatus`: `waiting` → `confirmed` | `timeout`, `setTimeout(poll, 3000)`, 60-second cutoff, a read-only `select('status')` that never writes). Platform Billing copies this shape directly: a `checkoutOrderId`/`checkoutStatus` pair reading `platform_orders.status`, the same three-state modal (spinner → checkmark, or a "still processing" third state), the same "close" behavior (no dismiss button while genuinely waiting, since there is nothing to dismiss to that would be more informative).

**Why the rejected options are worse.**
- **B (manual check)** adds a click the customer has no reason to know they need to make, for a wait that usually resolves in a few seconds anyway — worse than A for the common case, and no better than A for the slow case, since A already has a defined endpoint (the 60-second timeout).
- **C (no special screen)** fails the readiness review's own product test directly: "would they be confused about whether payment succeeded?" — landing on a page that gives no acknowledgment that something is in progress reads as broken, not calm.
- **D (real-time push)** would require reopening the Billing live-sync exclusion `OWNER_DOMAIN_IMPLEMENTATION_ARCHITECTURE.md` Section 8 already states is closed pending a separate governance decision — exactly the "redesign architecture" this mission forbids. It is also unnecessary: A already solves the actual product problem without touching that boundary at all.

**Resolved copy/behavior, inherited directly, not re-authored:** waiting state shows a spinner and "this can take a few seconds, don't close the app"-equivalent copy; confirmed state shows a checkmark and "your subscription is active"-equivalent copy, with a close action; timeout state (60s with no resolution) shows a "still processing, we'll follow up" state with the same close action — mirroring `checkoutWaitingText`/`checkoutConfirmedText`/`checkoutTimeoutText` exactly, restated for Platform billing's own subject (a Platform Subscription, not a Member Subscription).

# Decision 2 — Payment Success Before the Webhook Lands (refresh/close/reopen robustness)

**Options considered.**
- **A. Match the existing precedent's behavior exactly** — the polling state lives only in React state plus a one-shot URL query parameter (`?checkout=<id>`) that is stripped from the URL on first read; a hard refresh during the waiting window loses the polling modal, and the customer simply sees whatever the Billing screen's normal read shows until they revisit.
- **B. Additionally make the Billing screen itself pending-aware** — its own normal "current plan" read also checks for a recent pending Platform Order belonging to the Gym and shows an inline "processing" indicator if one exists, independent of the one-shot redirect.
- **C. Persist checkout state** (e.g., `localStorage`) so a hard refresh resumes the exact polling modal.

**Decision: A, plus B.** Keep the existing precedent's redirect-driven polling modal exactly as-is (Decision 1) — do not build C, a persistence mechanism the existing, live, working Member-billing flow has never needed. Add B as a small, natural extension: the Billing settings screen (already required by M10.5's own scope to show "current plan") reads Gym Commercial State and the Gym's own Platform Subscription/Order fresh on every render, exactly as every other read model in this domain already does (`OWNER_DOMAIN_IMPLEMENTATION_ARCHITECTURE.md` Section 8 — "no independent storage; a join across existing entities"). Extending that already-required read to also recognize "a pending Order exists and is recent" and show a small inline "payment processing" line is not a new mechanism — it is the same read, interpreted one additional way.

**Why the rejected option is worse.** C solves a problem the real system has never actually had — the existing Member-billing flow has run in production without session-persisted checkout state, and inventing one here would be exactly the kind of speculative mechanism `M10_IMPLEMENTATION_PLAN.md`'s own discipline (no preparation beyond what's needed, no parallel mechanism where one isn't required) warns against. B gets the same practical benefit (a refreshed or reopened tab is never confusingly stale) for the cost of one additional condition on a read the screen was always going to perform anyway.

# Decision 3 — Existing Paying Customer Presses Buy Again

**Options considered.**
- **A. RPC-level rejection** — `purchase_platform_plan` is called, and returns an error naming the invariant it would otherwise violate.
- **B. CTA-level prevention** — the Buy/purchase action is never rendered as clickable in the first place once a Gym is already `paying`; the Billing screen shows a read-only "active plan" summary instead.
- **C. Silent redirect to the upgrade/downgrade flow** — clicking Buy while paying is reinterpreted as "change plan."

**Decision: B, with A as the required defense underneath it, never the primary experience.** This is, again, a live, proven, existing pattern, not a new invention: `App.jsx`'s own Member-facing subscription screen already does exactly this — the "Choose Membership"/renew button is conditionally rendered only when there is *no* currently active subscription (`onlinePaymentsAvailable && abonamentInceput`); the moment a subscription is active, that entire branch is replaced by a read-only "Active Plan" card (plan name, valid-through dates, a status badge) with no purchase action anywhere on it. Platform Billing's own Billing settings screen copies this shape directly: a paying Gym sees its current Platform Subscription as a read-only summary; the purchase CTA simply does not exist on that render.

A still matters underneath B, exactly as `purchase_platform_plan`'s own stated invariant (`OWNER_DOMAIN_IMPLEMENTATION_ARCHITECTURE.md` Section 6.4 — "at most one currently-active Platform Subscription per Gym") requires: the RPC must reject the call if it is ever reached with an already-active Subscription in place (a stale tab, a race between two browser tabs, a replayed request), returning a clear error. This is defense-in-depth, not the primary user-facing design — an Owner should never actually see that error under normal use, because B already prevents the click.

**Why the rejected options are worse.** A alone (no CTA hiding) means every paying Owner sees a Buy button that always fails — confusing, and inconsistent with the existing, already-shipped, already-proven Member-facing pattern for the identical situation. C (silent redirect to upgrade/downgrade) quietly reinterprets one action as a different one the Owner didn't ask for, and — more importantly — upgrade/downgrade is explicitly a separate, not-yet-built milestone (M10.6); routing into it from M10.5 would be building against a milestone this mission's own discipline forbids preparing for.

# Decision 4 — Checkout Session Expiry (and the idempotency-key interaction)

**Options considered.**
- **A. Fix it now in Platform Billing's new code** — give the Stripe `idempotencyKey` a component that changes across genuinely distinct attempts (e.g., incorporate the Order's own `updated_at`/an attempt counter), so a retry after Stripe's own Session expiry always produces a fresh, usable Session rather than risking a stale one returned from Stripe's idempotency cache.
- **B. Copy the existing Member-billing key scheme exactly** (`checkout_session:${orderId}`, no attempt component), accepting the same latent risk that already exists, live, in production today.
- **C. Leave it entirely unaddressed and undocumented**, as it currently is everywhere in this codebase.

**Decision: A — Platform Billing gets a corrected idempotency key, incorporating an attempt-scoped component, not a straight copy of the existing scheme.** The reasoning that makes B look attractive elsewhere in this document — "an already-proven pattern is safer than a new one" — does not apply here, because B is not actually proven safe on this specific point; it has simply not yet failed in a way anyone has noticed. This review is the first place this risk has been named at all. Since Platform Billing is new code, unconstrained by anything already live, the correct move is the safer one: key on something that changes per genuine retry attempt (the simplest correct choice already available in the schema: the Platform Order's own row, re-derived per attempt, gives a natural per-attempt identifier without inventing a new column — e.g., a key composed from the Order id plus a coarse time bucket no finer than Stripe's own Session-expiry window, so a retry inside one still-valid Session collapses correctly, per Decision 1's dedup goal, while a retry after expiry is guaranteed a fresh key).

**Why the rejected options are worse.** B knowingly ships a newly-identified risk into a payment path carrying "the highest-sensitivity write path in this entire plan" framing (`M10_IMPLEMENTATION_PLAN.md`'s own words) when a fix costs nothing architecturally — the Financial Domain's own Section 3.7 principle ("reuse a proven mechanism") is about not reinventing what already works, not about copying a flaw nobody has yet validated as safe. C is worse still — an undecided, undocumented risk in the one payment path this whole review exists to make safe is precisely what "REQUIRES PRODUCT DECISIONS" was written to prevent from happening silently.

**Scope note, stated once:** this decision governs Platform Billing's own new idempotency-key scheme only. Whether the pre-existing Member-billing key scheme is separately revisited is explicitly out of scope here — flagged, not resolved, exactly as the readiness review already named it.

# Decision 5 — Retry Behaviour (general)

**Decision, composing the above rather than adding anything new.** "Retry" is not one behavior — it is three cases, each already resolved by an existing decision:
- **Retry while the original pending Order is still fresh** (inside Forge's own `pending_order_expiry_hours`-equivalent window and inside Stripe's own Session validity): reuse the same pending Order, exactly the proven `decideOrderReuse` shape from `create-checkout-session.ts` — no new Order, no new Subscription, collapsed before Stripe is even contacted a second time.
- **Retry after the pending Order has aged out of the reuse window, but the Gym is still not paying:** a new Order is created, exactly as `decideOrderReuse`'s own `reuse: false` branch already does today for Member billing — this is not a special case, it is what "the window expired" has always meant in the proven pattern.
- **Retry after Stripe's own Session expired specifically** (a narrower condition than Forge's own reuse window, per Decision 4): the corrected, attempt-scoped idempotency key (Decision 4) guarantees this produces a genuinely fresh Session rather than a stale one, regardless of which of the two cases above it falls into.

No fourth case exists. Nothing here is a new decision — it is the explicit statement that Decisions 1–4 already, together, cover every shape "retry" can take.

# Decision 6 — Stripe Product/Price vs. Inline `price_data`

**Options considered.**
- **A. Pre-created Stripe Product + Stripe Price per Platform Plan Version** — the mapping `PLATFORM_BILLING_MODEL.md` (M10.4) originally recommended.
- **B. Inline `price_data` on every Checkout Session creation call**, deriving amount/currency/name fresh from the already-fixed Platform Order each time — the actual, live, proven pattern `create-checkout-session.ts` already uses for Member billing.

**Decision: B.** This is the readiness review's own self-correction, now finalized: the live precedent does not use pre-created Stripe Price objects anywhere, and Principle 3.7 ("reuse a proven mechanism before inventing a parallel one") settles this the moment the two options are compared against what is actually running in production rather than against general Stripe best-practice reasoning in the abstract. `platform_plan_versions` needs no `stripe_product_id`/`stripe_price_id` columns. `purchase_platform_plan`'s Edge Function counterpart constructs `price_data` inline, from the same already-fixed `price_amount`/`currency` this domain already stores on the Version (M10.4, shipped), exactly mirroring `buildCheckoutSessionParams`'s own shape (`price_data: { currency, unit_amount, product_data: { name } }`).

**Why A is worse.** A adds two nullable columns, a synchronization concern (what happens if a Stripe Product/Price is created but the local row's write fails, or vice versa — a whole new partial-failure case B does not have, since B never creates a durable Stripe-side object at all), and a migration path this domain does not need, in exchange for a benefit (Stripe-side catalog visibility in Stripe's own dashboard) the existing Member-billing flow has never needed and never built. `docs/architecture/PLATFORM_BILLING_MODEL.md`'s own Stripe Mapping section should be treated as superseded by this decision.

# Self-Review — Attempting to Break Each Decision

**Decision 1, broken?** What if the customer closes the tab entirely during `waiting` and never returns? Nothing is lost — the webhook still lands, still writes the Platform Subscription/Order/Payment correctly, independent of whether any browser tab is open to observe it (Decision 1's polling is purely an observer, exactly like the Member-billing precedent it copies). The receipt email (already in M10.5's own scope) is what tells them afterward. Holds.

**Decision 2, broken?** What if two tabs are both open and polling/reading simultaneously? Both are read-only against the same authoritative row; there is no write conflict a second reader could cause. Holds.

**Decision 3, broken?** What if the Owner has two browser tabs open, one showing "no active plan" (stale) and clicks Buy in that stale tab right after paying in the other? This is exactly what Decision 3's RPC-level guard (A, as defense-in-depth) exists for — the call is rejected, not silently duplicated. The Owner sees an error in a genuinely rare, self-inflicted case, rather than a duplicate Subscription ever being created. Holds, because the defense-in-depth half of the decision was kept rather than dropped.

**Decision 4, broken?** What if the coarse time bucket is too coarse (spans longer than Stripe's own Session validity) or too fine (defeats Decision 1's own double-click dedup within a single still-valid Session)? This is a tuning question, not a decision left open — the bucket width is bounded on both sides by already-known, fixed values (Stripe's own Session-expiry default on the wide side; the moment-to-moment double-click window on the narrow side), so a correct value exists inside those bounds; picking the exact number is an implementation detail, not a product decision this document owes an answer to.

**Decision 6, broken?** What if Forge later wants Stripe-side reporting (Option A's one real advantage)? Nothing about B forecloses adding Stripe Products/Prices later — it is a strictly additive change if ever needed, not a decision that has to be made correctly upfront to avoid a future migration. Holds.

**Cross-decision check:** do Decisions 1–6 ever require a Member-Domain or Financial-Domain table, RPC, or webhook to be touched? No — every mechanism reused above (`decideOrderReuse`'s shape, the polling modal's shape, the CTA-hiding shape, `buildCheckoutSessionParams`'s inline-price shape) is copied as a *pattern*, into Platform Billing's own, separate schema and Edge Functions, exactly as `OWNER_ACTIVATION_ARCHITECTURE.md` Section 15 and Principle 3.2 require. No boundary named in either frozen document is crossed by any decision in this file.
