# M10.2 — Activation Dashboard: Final Product Revision

This document integrates the findings of the M10.2 Product Review into a single, final product specification. It changes nothing about frozen architecture, the Owner Journey, the Gym Lifecycle State machine, or any domain event. Everything below is a display, sequencing, and copy decision layered on facts and events that already exist. Where this document resolves an ambiguity the architecture left open (Dashboard Evolution), it resolves it as a product/UX choice, not a new technical decision.

**Compliance check, stated once, governing everything below:** no new table, no new RPC, no new lifecycle state, no new domain event is introduced anywhere in this document. Every behavior specified here is implementable using `gym_activation_state`, `gym_commercial_state`, the existing `FirstValueReached`/`OwnerActivated` events, and the existing M9 invitation mechanism, exactly as already frozen.

---

# Executive Summary

The Activation Dashboard has one job in its first render: convert the relief of finishing Bootstrap into one obvious action, without spending any of that momentum on re-explaining, re-deciding, or reviewing. This revision makes three changes to the milestone as originally scoped — a persistent confirmation header that answers the three non-negotiable questions in the first glance, full collapse of every optional item behind a single disclosure, and a same-email self-preview affordance for the Owner with nobody to invite yet — and resolves one open question (Dashboard Evolution: the screen evolves, it never changes identity). Nothing here requires new infrastructure. This is the last product document before engineering begins.

---

# Product Principles

Five rules, specific to this milestone, each a direct answer to a finding from the prior review:

1. **The Dashboard confirms before it asks.** The very first thing rendered is proof that Bootstrap worked — never a form, never a checklist, never a blank state. Confirmation comes first, action second.
2. **Exactly one required action is visible as primary at a time.** Before First Value: confirm the Waiver, then invite. After First Value: nothing required is left; the surface shifts to inviting a return, not demanding a task.
3. **Optional configuration is available, never competing.** If it doesn't move the Owner toward First Value or Activation, it does not share visual weight with what does — it is one tap away, never zero taps away.
4. **The Owner is never stranded.** Every state this screen can be in — including "I have nobody to invite yet" — has a specific, named, in-product answer. "I don't know what to do" is never an acceptable end state.
5. **Nothing here spends momentum re-explaining what already happened.** The Owner just proved intent (survived email verification, typed a Gym name, clicked through). This screen never asks them to reconfirm that intent — it acts on it immediately.

# Dashboard Behaviour

## The first 30 seconds — the non-negotiable goal, made concrete

The screen opens with a persistent, always-visible header, present for every Owner who has not yet reached Activation, containing exactly three facts in one glance:

- **The Gym now exists**, by name — not "welcome" or generic branding, the Owner's own Gym name, stated as an accomplished fact ("[Gym name] is live").
- **The trial is active**, stated plainly, not as a countdown-anxiety element — a simple, calm statement that a trial is running (`gym_commercial_state.trial_started_at`/`trial_ends_at` already carry this; no new fact is needed to say it).
- **What happens next**, immediately below, in the form of the single primary action available at the Owner's current stage (see First Value Journey).

This header is the direct, literal fix for the non-negotiable goal: all three required understandings are satisfied by one render, not inferred from separate parts of the screen.

## What is never shown at this stage

Optional configuration, class-schedule setup, branding, payment connection, co-admin invitations — none of these appear anywhere in the primary view before First Value. Their existence is real and reachable, but reachable is not the same as visible (see Cognitive Load Decisions).

# First Value Journey

Two required actions, unchanged from the original scope, re-sequenced around the confirmation header above:

1. **Confirm your Waiver.** Pre-filled from template, reviewed and confirmed, not composed. This step's framing must do real work it currently doesn't get credit for: it should read as *protection*, not paperwork — the goal is an Owner who understands this exists to protect them and their members, not an Owner filling out a form because the product demanded one. This is a copy/tone requirement on an already-specified step, not a new step.
2. **Invite your first Member.** The single action that produces First Value. Shown as the clear, singular primary call-to-action the instant the Waiver is confirmed — never competing with anything else on screen.

**Every element on this screen is tested against one question: does this move the Owner toward First Value?** Everything that fails that test (the five optional items) is removed from view, not merely de-emphasized — see Cognitive Load Decisions. Nothing else survives in the pre-First-Value view.

**The moment First Value is reached:** the mandatory notification already specified in `OWNER_ACTIVATION_ARCHITECTURE.md` Section 7 fires, exactly as frozen. Its content — still within the scope of an already-specified notification, not a new one — must include one forward-looking line seeding the next visit (e.g., naming that the Owner can come back and see their new Member show up on the roster). This is a content requirement on an existing notification, not a second notification.

# Activation Journey

First Value and Activation are different milestones, and the screen must visibly behave differently for each — not just internally track them differently.

**Between First Value and Activation:** the checklist has already collapsed to the lighter "Getting Started" panel (per the frozen two-stage retirement). This is the one place M10.2's original scope under-served Activation, and the fix is entirely a content addition to an already-specified panel: rather than a passive, shrinking task list, this panel actively names the next Activation-qualifying action available to the Owner right now — inviting a second Member, checking who's accepted, reviewing the roster — framed as "come back and do this," not "you still have this left." The panel's job changes from *reducing anxiety about unfinished setup* to *creating a specific reason to return*.

**Does every remaining element increase the probability of a return visit?** Tested explicitly:
- The lighter panel's forward-looking prompt — yes, that is its entire purpose now.
- The collapsed optional-items disclosure — no direct effect either way; correctly excluded from being framed as an Activation lever.
- The header's trial-status line — indirectly yes; a calmly-stated active trial is a legitimate, honest reason to return without manufacturing urgency.

No fake activation is introduced anywhere. A returning Owner who only reopens the app and looks around does not activate — Activation still requires the real operating action the frozen state machine already defines. This document only ever tries to make that real action more *likely*, never substitutes for it.

# Cognitive Load Decisions

**Strongest available solution, chosen over the original "visible but secondary" treatment: full collapse.** All five optional items (customize Plan, upload logo, invite co-admin/coach, connect payments, set up a class schedule) live behind a single, closed-by-default disclosure — "More setup (optional)" or equivalent — visible as one unobtrusive line, not as five individually-weighed items. This satisfies Principle 3.15 (configuration never blocks exploration) exactly as fully as the original treatment did — nothing is hidden behind more than one tap — while removing five simultaneous micro-decisions from the highest-leverage minutes of the relationship.

**Grouping rationale:** all five belong in one disclosure, not several, because none of them individually competes for urgency with First Value — splitting them into multiple groups would only reintroduce the visual weight this change exists to remove, for no added clarity.

**What stays permanently deferred, not merely collapsed:** none of the five optional items ever becomes required, at any stage, for any Owner. Their existence in the collapsed disclosure is a permanent home, not a staging area for a future required step.

# "No Members Yet" Behaviour

The pre-launch Owner (already named in `OWNER_ACTIVATION_ARCHITECTURE.md`'s own persona research) can be structurally unable to complete the one required First-Value action through no fault of the product. The product behavior, faithful to every constraint:

- **The Activation definition does not change.** A self-directed test invitation still does not count as First Value — this is already enforced structurally (the qualifying-identity check already excludes the Owner's own identity) and nothing here touches that.
- **No fake activation is introduced.** The affordance below is explicitly, visibly labeled as a preview, never presented as satisfying the real requirement.
- **First Value is not weakened.** The bar for the real thing stays exactly where it is.

**The specific, minimal addition:** directly beneath the "Invite your first Member" action, a secondary, clearly de-emphasized line offers to preview the experience — "Nobody to invite yet? Send yourself an invite to see exactly what your Members will see." This reuses the identical, already-existing invite mechanism (the Owner simply invites their own email address) — zero new scope, zero new RPC, zero new table. The resulting notification/UI must never claim this satisfies First Value; it is framed, visibly, as a preview, not a milestone.

This gives the pre-launch Owner a genuine, honest, non-blocking action to take on day one — building product confidence and familiarity — without ever letting the system, or the Owner, mistake it for the real thing.

# Dashboard Evolution Decision

**Decision: (A) — the Dashboard remains the same screen; its content evolves as the Gym progresses through the Activation axis. It never transitions to a structurally different screen.**

**Justification:**
- **Product goal.** The non-negotiable 30-second goal depends on the Owner's mental model of "this is where I check on my Gym" staying stable. Relocating them to a different screen exactly when they've earned momentum — reaching First Value, then Activation — fights that goal at the precise moment trust should be compounding, not resetting.
- **Reading of the frozen text.** `OWNER_LIFECYCLE_STATE_MACHINE.md`'s own language — onboarding scaffolding "replaced by the Owner's real operating dashboard" — is satisfied exactly as well by content changing within one persistent surface as by a route change, and the content-evolves reading requires strictly less technical surface area to build and maintain than standing up a second, structurally distinct screen. Where a reading of frozen text is genuinely open, the interpretation that requires *less* new technical scope is the correct one under this document's own stop conditions.
- **Consequence.** One screen, three content states, driven entirely by already-existing data (`gym_activation_state.activation_state`): full checklist (pre-First-Value) → lighter panel with forward-looking prompt (post-First-Value, pre-Activation) → full operating view with no onboarding scaffolding at all (post-Activation). No new route, no new component identity, no re-orientation cost to the Owner.

This decision is frozen. A future milestone that wants a genuinely separate operating surface is a new, explicit product decision, not an extension of this one.

# Success Metrics

Minimum set worth actually optimizing — each with a direct, stated product purpose, vanity metrics rejected explicitly:

1. **Time to First Invitation Sent.** Direct measure of whether the confirmation-first, one-action-visible design actually converts momentum into action. Purpose: catches regressions in cognitive load immediately, before First Value Rate even has time to move.
2. **First Value Rate.** The domain's own central KPI — % of Bootstrapped Owners reaching a qualifying Final Commit. Purpose: the single number this entire milestone exists to move.
3. **Return-within-48h-of-First-Value Rate.** Leading proxy for Activation, measurable well before Activation itself fires. Purpose: directly tests whether the Activation Journey's forward-looking prompts are working, independent of whether a full Activation-qualifying action follows.

**Explicitly rejected as an optimization target:** raw Checklist Completion Rate (rewards optional-item completion with no bearing on outcomes that matter) and any metric counting self-preview invitations as if they were real invitations (would silently corrupt First Value Rate's own meaning). Waiver-step time/abandonment is worth *watching* diagnostically but is not a target in itself — it exists to explain a First Value Rate problem, not to be moved directly.

# Final Product Changes

Relative to the milestone as originally scoped, four changes, all display/content/sequencing, none architectural:

1. Added a persistent confirmation header (Gym name + trial status + current primary action) — new content requirement, no new data.
2. Optional items moved from "visible, secondary" to "fully collapsed behind one disclosure" — display change only.
3. Added a self-preview affordance for the no-members-yet Owner, reusing the existing invite mechanism unmodified — copy and UI only.
4. Added a forward-looking, Activation-oriented content requirement to the already-specified First-Value notification and the already-specified lighter "Getting Started" panel — content only, zero new events or notifications.

Plus one frozen decision: Dashboard Evolution resolved as (A), same screen, evolving content.

# Product Self-Review

Applied to this revision specifically, not the original:

**Would it create confidence?** Yes — the confirmation-first header directly answers the doubt a returning-from-email-verification Owner is most likely to carry ("did that actually work?") before anything else competes for attention.

**Would it reduce abandonment?** Yes, on the two points most likely to cause it: cognitive overload from optional items (fixed by full collapse) and the pre-launch Owner's dead end (fixed by the self-preview affordance). The Waiver step remains an honest, irreducible friction point — no revision removes it, because none can; the tone requirement is the correct, available lever, not a fix.

**Would it create momentum?** Yes for the first five minutes (unchanged focus, less competing noise). Meaningfully improved for the days after First Value, where the original scope had almost nothing — the lighter panel's forward-looking prompt is a real, if modest, answer to a gap the first review found and this one closes without new infrastructure.

**Would it naturally guide the Owner toward becoming a paying customer?** Indirectly, correctly, and no further than that — this milestone still never mentions payment (correctly out of scope until M10.5), but a higher First Value Rate and a higher return rate are the two inputs everything downstream in the trial-to-paying funnel depends on. This document does its part by moving those two numbers; it does not, and should not, try to do the funnel's later job.

No further changes identified. This revision is ready to build.
