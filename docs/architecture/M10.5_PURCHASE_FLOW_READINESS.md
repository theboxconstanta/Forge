# M10.5 — Platform Purchase Flow: Execution-Readiness Review

This document reviews only whether M10.5, as scoped in `M10_IMPLEMENTATION_PLAN.md` Section 6, is ready for engineering to begin. It does not implement, redesign, or extend anything. Where the frozen documents already answer a question, that answer is cited, not re-derived. Where nothing answers a question, that gap is named, not filled.

**Grounding, stated once:** this review does not rely on architectural claims alone. Every reuse claim M10.5's own text makes ("Section 12.1's three-layer defense," "the same three-step verification Financial Domain's webhook already performs") was checked against the actual, live, production code it claims to reuse — `supabase/functions/stripe-webhook/index.ts`, `supabase/functions/create-checkout-session/index.ts`, and the `payments_provider_reference_unique` constraint. Every claim below is marked Verified (checked against real code or a frozen document's literal text), Reasoned (a sound inference from Verified facts), or a named gap.

---

# Executive Summary

The money-safety core of M10.5 is in excellent shape: immutability, attestation-authority, tenant isolation, and duplicate-delivery idempotency are not just architecturally asserted — they are already live, proven, working code in the Financial Domain's own Checkout/webhook pair, and M10.5's own text correctly identifies this pair as the pattern to copy. That is the hard part of "accept real money safely," and it is solved.

What is not yet fully decided is a smaller, more specific set of things: how the customer-facing pending-payment window actually resolves (given Billing is explicitly excluded from real-time sync), what happens when an already-paying Owner clicks Buy again, whether M10.5 owes the codebase a fix for a genuine, newly-found latent risk in the existing idempotency-key scheme, and one real inconsistency between this session's own prior `PLATFORM_BILLING_MODEL.md` guidance and the actual, proven Stripe integration pattern already in production. None of these require new architecture. All of them are answerable in a short product/engineering conversation, not a redesign.

**Verdict: M10.5 REQUIRES PRODUCT DECISIONS** — a small, enumerated set, not a re-scoping.

# Purchase Flow Review

Walking the full path the review requested, transition by transition.

**Anonymous visitor → Pricing page.** Live, verified — M10.4, already shipped, public, no purchase action.

**Pricing page → Start Free Trial → Signup → Verification → Bootstrap → Dashboard.** Entirely M10.1/M10.1a/M10.1b/M10.2 territory, already shipped and out of this review's scope. One connection point worth naming: nothing in M10.4's Pricing page links to Signup today (a decision explicitly deferred out of M10.4's own scope, per its own implementation report) — meaning the diagram's first arrow ("Pricing page → Start Free Trial") is not yet a real, clickable path anywhere in the product. Not a defect in M10.5's own scope, but the diagram in this review's prompt assumes a connection that does not exist yet.

**Dashboard → Buy Forge.** `OWNER_ACTIVATION_ARCHITECTURE.md` Section 14 names two, and only two, moments this entry point is allowed to appear: a contextual soft-prompt right after First Value, and a hard-prompt backstop at trial expiry (the latter is M10.8's job, not M10.5's). M10.5's own Frontend impact text names only "Billing settings (current plan, purchase CTA)" — a generic, always-reachable settings screen. It does not explicitly commit to building the first, contextual moment. **Named as a gap below.**

**Buy Forge → Stripe Checkout.** Verified reusable: `create-checkout-session/index.ts` already implements exactly this transition for Member billing — Order-first, then Stripe contacted, with a reuse-window for an existing pending Order and a deterministic Stripe `idempotencyKey`. M10.5's own text does not explicitly cite this specific mechanism by name (it cites the webhook's three-layer defense explicitly, but not this pre-webhook layer). **Named as a gap below** — the mechanism exists and is proven, but is not yet explicitly designated as the pattern M10.5 copies.

**Stripe Checkout → Webhook → Payment → Subscription.** Verified, thoroughly: `stripe-webhook/index.ts`'s four-step sequence (verify signature → re-derive Order from Forge's own record → confirm claim matches → invoke the same RPC any other caller would) is real, live code, and `OWNER_DOMAIN_IMPLEMENTATION_ARCHITECTURE.md` Section 7's Edge Function boundary table already assigns this exact shape to `platform-billing-webhook`. The three-layer idempotency defense (Financial Domain Section 9.1) is grounded in a real, live unique constraint (`payments_provider_reference_unique`) with a catch-and-return-existing-row pattern in `register_payment`'s own SQL — not merely described in prose.

**Payment/Subscription → Access.** Explicitly, correctly out of scope — M10.5's own text and Section 15's phase table both state access is never blocked by anything M10.5 does; that is M10.8's job, deliberately last.

# Product Review

- **Would a Gym Owner trust this flow?** Reasoned yes — the underlying mechanism is the same one already handling real Member payments in production today, not a new, unproven design.
- **Would they understand what happens next?** Depends entirely on the pending-state gap named below. Without a resolved answer to "how does the pending screen become the confirmed screen," this cannot be answered yes with confidence.
- **Would they ever be confused about whether payment succeeded?** Same dependency — this is the single most product-relevant open question in this review.
- **Would they accidentally pay twice?** Reasoned no, with high confidence — the reuse-window, the Stripe idempotency key, and the webhook's three independent layers together make this a well-defended case, not a single point of failure.
- **Would they know where to go afterwards?** Reasoned, adequately — `success_url` returns to the app; M10.5's "purchase-confirmed" state covers the immediate moment. Deeper "what's different now" messaging is a reasonable candidate for a later polish pass, not a blocker (the same pattern M10.2's own Dashboard followed).

# Missing Decisions

Six items. Each is small in scope; none requires new architecture. Per this review's own instruction, no solution is proposed here — each is named, with why it matters and what a resolution would need to state.

1. **The purchase-pending → purchase-confirmed UI transition mechanism is not decided.** `OWNER_DOMAIN_IMPLEMENTATION_ARCHITECTURE.md` Section 8 explicitly excludes Billing read models from real-time live sync ("follows the identical precedent" as the M13.2 Financial-Domain exclusion) — meaning the Owner will not be automatically pushed from "pending" to "confirmed" the way most of this app's other data now updates live. M10.5's own text names both UI states but not how the transition between them happens: polling, a manual "check status" action, or a page the Owner is expected to simply revisit. This is the single most product-relevant open question in this review — it directly determines whether an Owner mid-Checkout can ever be confused about whether their payment succeeded.

2. **What `purchase_platform_plan` does when called by an already-Paying Owner is not decided.** The invariant it must preserve is stated (Section 5.3); the specific caller-facing behavior when that invariant would otherwise be violated is not.

3. **Whether the after-First-Value contextual soft-prompt (`OWNER_ACTIVATION_ARCHITECTURE.md` Section 14) is in M10.5's own scope, or a later polish pass, is not decided.** M10.5's Frontend impact clearly describes a generic, always-reachable Billing-settings CTA. It does not clearly commit to the specific, contextual, moment-triggered prompt Section 14 names as the "correct first moment" to offer payment.

4. **Whether Platform Billing's Stripe Checkout Session reuses the exact `success_url`/`cancel_url` shape already proven for Member billing is not stated.** The existing precedent (same URL for both, differentiated by a query parameter) is a real, working, deliberately simple design — but M10.5's own text is silent on whether Platform Billing follows it.

5. **A genuinely new finding, not previously flagged anywhere: the existing Stripe `idempotencyKey` scheme (`checkout_session:${orderId}`, keyed only by Order ID) does not account for Stripe's own Checkout Session expiry.** If a customer retries a purchase after their original Stripe Session has expired but within Stripe's own idempotency-key retention window, requesting a new Session with the same key could return the stale, already-expired Session object rather than a fresh, usable one. This risk already exists, live, in the Member-billing flow — it is not introduced by M10.5, but M10.5 is the first place this review has surfaced it as an explicit, undecided question rather than an implicit assumption. Whether to fix it in M10.5 (since Platform Billing is new code, unconstrained by the existing Member-billing implementation) or treat it as a pre-existing, separately-tracked issue is a real decision, not something this review resolves.

6. **This session's own prior `PLATFORM_BILLING_MODEL.md` (M10.4) Stripe-mapping guidance likely contradicts the actual, proven implementation pattern, and should be reconciled before M10.5 begins.** That document recommended a pre-created Stripe Product + Stripe Price per Platform Plan Version. The actual, live, working Financial Domain precedent (`create-checkout-session.ts`) does not use pre-created Stripe Price objects at all — it constructs `price_data` inline on every Session-creation call, deriving amount/currency/name fresh from Forge's own already-fixed Order. Per Principle 3.7 ("reuse a proven mechanism before inventing a parallel one"), the inline pattern is the stronger candidate — which would mean `platform_plan_versions` likely needs no `stripe_product_id`/`stripe_price_id` columns at all. This is named here as a real self-correction to surface before implementation starts, not a new design produced by this review.

# Engineering Readiness

Everything load-bearing for financial safety is ready: the schema shapes (Section 5.3/5.4), the RPC authorization model (Section 11), the audit requirements (Section 13), and the failure-recovery mechanism (Section 12) are all fully specified and, critically, already proven in equivalent, live, production code — this is not a case of trusting an architecture document's aspiration. The six items above are the only things standing between this review and an unqualified "ready." All six are answerable in a short conversation; none requires re-opening `M10_IMPLEMENTATION_PLAN.md`, `OWNER_DOMAIN_IMPLEMENTATION_ARCHITECTURE.md`, or the Financial Domain's own frozen architecture.

One documentation-hygiene note, not a blocker: `OWNER_DOMAIN_IMPLEMENTATION_ARCHITECTURE.md` Section 15's own "Implementation Phases" list still uses the labels "M10.4" and "M10.5" for a six-phase grouping that `M10_IMPLEMENTATION_PLAN.md`'s own introduction explicitly states it superseded with an eight-milestone refinement — under Section 15's old numbering, "M10.5" means the webhook bundled together with dunning/Past-Due, which is *not* what "M10.5" means in the document actually governing this review. `M10_IMPLEMENTATION_PLAN.md` is unambiguously the later, self-declared authority on this point, so this is not a live contradiction requiring a decision — but Section 15 reads misleadingly in isolation and would benefit from a one-line pointer to the newer numbering.
